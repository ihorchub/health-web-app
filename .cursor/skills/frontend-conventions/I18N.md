# i18n (EN / UK)

## Library

`react-i18next` with **manual** locale files. No machine translation.

## What switches with language

| Kind | Behaviour |
|------|-----------|
| UI chrome (buttons, titles, empty states, errors, labels) | `t('namespace:key')` from UK/EN JSON |
| Platform catalogs (specialty **ids**, appointment statuses, curated enums) | Localize via **i18n keys by id** (e.g. `auth:specialties.family_doctor`), not by storing one language string in UI state |
| Reference lists from API (cities, clinics) | Display **what API returns for the active locale** (`Accept-Language` / `lang` when BE supports it). Until dual names exist on BE, show the single `name` field as-is — do not invent client-side city translation |
| User-entered data (name, free-text reason, review body) | **As typed** — does not change when toggling UK/EN |
| Doctor / clinic long copy (bio, about) | **Dual authored fields** from backend (e.g. `descriptionUk` + `descriptionEn`, or equivalent). Doctor profile edit = **two textareas** (UK + EN). UI shows the field for the **active app language**, with fallback to the other if empty. **Never** machine-translate |

## Full remount on language change

When the user toggles UK ↔ EN, **remount the routed app tree** (`key={language}` on `RouterProvider` or equivalent) so every screen re-initializes with the new locale: `t()`, date/number formatters, and any content picked from dual fields / refetch with new `Accept-Language`.

Do not rely only on scattered `t()` re-renders if filters, mock mappers, or memoized labels can stay stale.

## File layout

```
src/i18n/
  locales/
    uk/
      common.json
      auth.json
      search.json
      booking.json
      patientRoom.json
      doctorDay.json
      profile.json
      workingHours.json
    en/
      (same namespaces)
  index.ts
```

Default language: **uk**. Persist user choice. Send the same locale to API (`Accept-Language` or agreed param) for localized **catalog/content** once BE supports it.

## Rules

- No raw user-facing strings in JSX — use keys
- Author both `uk` and `en` yourself (or leave EN empty only with explicit fallback policy)
- Namespaces by area/SCR — do not dump everything into one file
- Specialty chips/filters/cards: use **specialty id** + `t('…specialties.' + id)`; ignore API `name` for display when i18n catalog exists
- Names (`firstName` / `lastName`) stay as stored — not translated
- Mocks must include dual description fields when the entity will have them on BE (see DATA-FETCHING.md)
